- (constraint) Final PRD and UX spines bind the architecture: H/P/D/I journey, Odoo staff/chat/SOP review, separate Portal/form/Dashboard web surfaces, human approval for AI, web online-only, role-scoped ticket access, SLA/audit/daily snapshots.
- (constraint) Brownfield seed exists: Docker Compose with Odoo Community, Node-RED, PostgreSQL, Superset, FastAPI/Haystack, Qdrant and Ollama under services/h_human, p_process, d_data, i_intelligence. Existing code is skeletal and is evidence of direction, not proof of implemented PRD behavior.
- (constraint) Repository and contest constraints: AGPL-3.0 project, open-source build from source, public dependency/license inventory, reproducible Docker Compose demo and contribution path that does not require the full AI stack for local changes.
- (decision) The P-layer business core owns ticket lifecycle and is the only component allowed to mutate canonical ticket state. Odoo, Portal, Dashboard, Node-RED and I-layer AI call explicit APIs or consume events; they must not write ticket tables directly. This prevents conflicting assignment, SLA, status and audit histories.
- (decision) Use a hexagonal TypeScript process core exposed through Fastify. Domain/application code contains assignment, SLA, lifecycle, CSAT and approval invariants; PostgreSQL and external systems are adapters. Node-RED is an integration/scheduling adapter and must not duplicate domain rules.
- (version) Verified 2026-09-19 from official sources: Node.js 24.21.0 LTS, Fastify latest 5.12.5, Node-RED 5.0 released 2026-06-09. Seed may pin compatible patch versions; source URLs: nodejs.org/en/blog, fastify.dev/docs/latest, nodered.org/blog/2026/06/09/version-5-0-released.
- (decision) Keycloak is the single OpenID Connect identity provider. The immutable OIDC subject is the cross-system actor ID; email is not an identity key. P enforces resource-level authorization on every command/query, Odoo enforces its UI groups, and analytics receives only authorized scopes. Demo role switching uses isolated authenticated browser sessions, never an in-product impersonation switch.
- (version) Verified 2026-09-19 from official sources: Keycloak server 26.7.4 current; OCA server-auth provides auth_oidc (Odoo branch compatibility must match the pinned Odoo major). Sources: keycloak.org/downloads and github.com/OCA/server-auth.
- (decision) Use one Next.js web shell/BFF for DX-Portal, H/P landing pages, public ticket form and the unified D/I director dashboard. D embeds scoped Superset content using server-issued guest tokens; I is native Next.js UI calling P. Browser clients do not call PostgreSQL, Superset admin APIs or I services directly. OIDC session credentials remain in secure HttpOnly cookies.
- (version) Verified 2026-09-19 from official sources: Next.js 16.3.3 Active LTS, React 19.3, and Superset supports Embedded SDK with server-fetched guest tokens. Sources: nextjs.org/blog, react.dev/versions, superset.apache.org/user-docs/using-superset/embedding.
- (decision) AI is advisory only. P/D deterministic rules decide whether evidence meets the 3 overdue tickets/7 days/>60 business minutes threshold. I classifies description or generates an explanation/SOP draft from sanitized DTOs and approved knowledge; it cannot mutate tickets, publish SOPs or send external messages. Results return through authenticated idempotent P commands and require the PRD human approvals.
- (decision) P owns an attachment-storage port. The demo uses a dedicated filesystem volume; PostgreSQL stores attachment metadata, checksum, media type, size and opaque storage key only. Upload/download always goes through authorized P endpoints, files are outside the web root, limited to allowed image/PDF content and 10 MB. An S3-compatible adapter is deferred until multi-host deployment.
- (decision) Odoo stores projections/work items and integration references, not canonical ticket state. Odoo actions call P commands; async events refresh the projection. P also owns SOP draft/approval lifecycle and approved knowledge versions; Odoo supplies the reviewer UI, Resources reads only published versions, and I indexes only published versions.
- (decision) Demo deployment is one Docker Compose host on a private bridge network. A single ingress/reverse proxy is the only public entry point; PostgreSQL, P internal ports, Superset admin APIs, Node-RED editor, Keycloak admin, Qdrant and Ollama are not exposed publicly. Kubernetes, HA and multi-region are deferred until post-demo scale requires them.
- (version) Verified 2026-09-19 from official sources: PostgreSQL 16.15 is the current supported 16.x minor (support through 2028-11-09); Superset 6.0.0 official docs; Qdrant 1.18.2 latest validated; Haystack 3.1.1 latest; FastAPI 0.141.1 latest; Caddy 2.11.4 latest; Ollama 0.34.1 latest. Existing older Compose pins are migration inputs, not final pins. Sources: postgresql.org/support/versioning, superset.apache.org/user-docs/6.0.0, qdrant.tech documentation changelog, GitHub official release pages for deepset-ai/haystack, caddyserver/caddy, ollama/ollama, and fastapi.tiangolo.com/release-notes.
- (decision) All P APIs use versioned REST /api/v1 with OpenAPI. Mutating commands require Idempotency-Key and aggregate version preconditions; concurrent stale writes return RFC 9457 problem details. Domain IDs are UUID, human ticket codes are separate, timestamps are UTC ISO 8601, and business-time calculations use Asia/Ho_Chi_Minh plus configured calendars.
- (decision) Committed P transactions append a versioned integration event to a PostgreSQL outbox in the same transaction. A worker publishes at-least-once with retry/dead-letter state; consumers deduplicate by event_id. Node-RED may route delivery and schedules only after commit and may never infer or mutate domain state on its own.
- (decision) The demo uses one PostgreSQL 16 server with separate databases and least-privilege users for Keycloak, Odoo, P, and Superset metadata. P alone owns canonical schemas; Superset receives read-only reporting views/snapshots, Odoo receives projections, and AI receives sanitized DTOs. No component reads another component's private tables.
- (decision) Keycloak uses Authorization Code plus PKCE for browser sessions and client credentials for service calls. The Next.js BFF keeps Secure HttpOnly SameSite=Lax sessions; every service validates issuer, audience and scopes. Public form and CSAT links use rate limits plus unguessable single-purpose tokens and never authorize by ticket code.
- (decision) Reporting definitions live in P-owned versioned SQL views and a daily snapshot job; Superset only visualizes them. Dashboard state must reflect committed records within 60 seconds. Row/group scope is derived from the authenticated subject before a Superset guest token or native I response is issued.
- (decision) Use Caddy as the sole ingress. Compose separates public, application and data networks; only Caddy publishes host ports. Admin surfaces bind to localhost or an opt-in admin profile. Secrets have no default credentials and arrive via ignored env/secret files; wildcard CORS and latest image tags are forbidden.
- (decision) Repository execution profiles are core (P plus PostgreSQL and test doubles), demo (web, Keycloak, Odoo, Node-RED, Superset), and ai (Haystack, Qdrant, Ollama). Core tests and first-contribution work must not download or run a model. Container images and package lockfiles are pinned and dependency/license inventory is generated in CI.
- (decision) Operational records use structured JSON logs with correlation_id, actor_sub, aggregate_id and event_id but never customer content, attachment bodies, tokens or prompts. Audit records are append-only. Health/readiness checks cover DB and required downstreams; retries are bounded and observable.
- (decision) Backup design: daily 00:30 Asia/Ho_Chi_Minh logical dumps for P/Odoo/Keycloak/Superset metadata plus attachment, Odoo filestore and published-knowledge volumes; encrypt and copy to a second location; retain 7 daily, 4 weekly and 12 monthly copies; run and record a monthly restore test. Qdrant is rebuildable from published knowledge and embedding manifests; model/cache artifacts are reproducible rather than primary backup data.

- (decision) Fair assignment is a deterministic atomic P transaction: available staff in provisional-type group, one active/reserved ticket maximum, minimum accepted-assignment count, ascending-ID rotation on ties, temporary reservation, FIFO queue, and counter increment only on confirmed responsibility.
- (decision) Universal ticket lifecycle is WAITING to IN_PROGRESS to CLOSED; confirmation gates processing, result gates assignee-only close, closed never reopens, SLA includes all waiting during configured business calendar, and low CSAT creates one lead review.
- (decision) Authoritative integration contracts are checked-in OpenAPI and event JSON Schemas. P outbox posts authenticated HTTP to Node-RED, Node-RED calls idempotent Odoo endpoints, and aggregate_version plus checkpoints/gap resync handles ordering and projection rebuild.
