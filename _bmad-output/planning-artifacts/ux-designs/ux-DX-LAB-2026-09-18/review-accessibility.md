# Accessibility review — DX-OS UX

Reviewed `DESIGN.md`, `EXPERIENCE.md`, and PRD FR-4/7/8/9/10/11/12 on 2026-09-18. This is a review of the UX contracts, not a claim that a running product passes WCAG. Contrast ratios below are calculated from the current draft color tokens.

## Findings

| Severity | Location | Finding and concrete fix |
|---|---|---|
| High | `EXPERIENCE.md` → Component Patterns / State Patterns / Accessibility Floor | Form errors mention a summary and field messages, but the contract does not say how those messages are programmatically associated with fields or announced. Specify a text error summary linked to each invalid field, `aria-invalid`/`aria-describedby` (or equivalent native semantics), focus to the summary after rejected submit, and preserve the entered values. For asynchronous submit, announce success with the ticket code once and guard duplicate submission while pending. |
| High | `EXPERIENCE.md` → Dashboard D/I / Accessibility Floor | Chart legend plus a route to source tickets does not guarantee that a screen-reader user can understand trends or proportions. Give every chart a descriptive title and a nearby text/table equivalent containing the same filtered values, units, period, and sample size; expose filter changes and “data last updated” as text. Keep source-ticket links subject to FR-9 permissions. |
| High | `EXPERIENCE.md` → Odoo staff and SOP flows / Responsive & Platform | The spine delegates behavior to “Odoo native” but has not verified that the configured widgets support keyboard and phone use for confirm category, record step, Close, and approve SOP. Define acceptance checks for these exact journeys at 320 CSS px and 200% zoom, with keyboard-only and screen-reader runs; if a native widget fails, provide an accessible configuration or replacement before demo. Do not mark this as satisfied solely because Odoo is used. |
| Medium | `EXPERIENCE.md` → State Patterns / Interaction Primitives | Several state changes are visual-only in the contract: AI suggestion arriving, assignment changing, dashboard refreshing, permission revoked, SOP approval. Require a persistent text state and a polite status announcement for noncritical changes; use focus management on navigation or blocking permission errors. A permission-denied page should state the user's safe next action (return or contact administrator) without revealing ticket details. |
| Medium | `EXPERIENCE.md` → Component Patterns / Responsive & Platform | “Vùng chạm đủ rộng” lacks an actionable size and spacing check, especially for dense Odoo ticket actions and D/I tabs on a phone. Specify a minimum target of 24×24 CSS px with separation, with 44×44 preferred for primary mobile actions; verify no horizontal scroll at 320 CSS px and 200% zoom and that controls are not obscured by browser chrome or sticky bars. |
| Medium | `DESIGN.md` → Colors / Components | Current token pairs are strong (`primary`/white ≈5.96:1, `accent`/`on-accent` ≈6.14:1, `ink`/white ≈15.57:1), but semantic warning/error/success, borders, disabled, and focus tokens remain unspecified. Add those pairs and measure actual rendered text, icons, chart marks, and focus outlines on their real backgrounds; require at least 4.5:1 normal text, 3:1 large text and nontext indicators. Do not rely on the current primary/accent ratios to cover every state. |
| Medium | `EXPERIENCE.md` → Dashboard filters / Key Flows | Filter updates and D↔I navigation lack keyboard and announcement detail. Make each filter explicitly labeled with its selected value; preserve focus when data updates, announce the changed result count and timestamp, and provide visible text navigation between D and I. Avoid focus jumping to the first KPI after every filter change. |
| Low | `EXPERIENCE.md` → Email đóng + CSAT | The 1–5-star choice needs an explicit accessible name and selected value. Use a labeled radio group with textual options “1 sao” through “5 sao”, keyboard selection, and a text confirmation after submit. Do not convey the score solely with star glyphs. |

## Coverage judgment

The spines cover the named routes, textual status labels, basic keyboard intent, and mobile layout direction. The three high findings are acceptance-level gaps for the demo journeys. They can be resolved in the UX contracts before implementation, then verified against actual Odoo configuration and rendered pages.
